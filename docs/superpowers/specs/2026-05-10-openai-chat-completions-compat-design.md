# OpenAI Chat Completions Compatibility Design

**Date:** 2026-05-10
**Status:** Approved

## Motivation

Current single-test execution is exposed through `POST /api/v1/tests/sync`, which requires AutoAgent-specific request fields such as `mode`, `target_profile`, and `new_session`. This is workable for internal callers, but it prevents direct use from OpenAI-compatible client libraries such as the Python SDK. The goal of this change is to add a small OpenAI-compatible HTTP surface that lets a caller reuse the existing execution pipeline without learning the internal request model first.

The first target is `client.chat.completions.create(...)` with a non-streaming request. This should be enough for a user to authenticate once with the existing JWT flow, point the SDK `base_url` at AutoAgent, and trigger the current sync test path through an OpenAI-shaped request.

## Scope

- Add `POST /v1/chat/completions`
- Reuse the existing JWT bearer token flow from `/api/v1/auth/login`
- Reuse the existing sync test execution path used by `/api/v1/tests/sync`
- Map OpenAI-style requests into internal `Sample` objects
- Map internal `SampleResult` objects into OpenAI-style `chat.completion` responses
- Support AutoAgent execution extensions through request-body extension fields:
  - `new_session`
  - `timeout_sec`
  - `retry`
  - `dry_run`

## Out Of Scope

- `POST /v1/responses`
- Streaming (`stream=true`)
- Tool calling, functions, audio, multimodal content blocks, or structured output
- Multi-turn request semantics from full OpenAI `messages` history
- Changes to executor behavior outside response selection for the compatibility response
- Changing `/api/v1/tests/sync` request or response schema

## High-Level Approach

The compatibility layer is a protocol adapter, not a second execution engine. The new route accepts an OpenAI-like request, validates it against the intentionally narrow first-version contract, resolves the target profile, builds an internal `Sample`, and then calls the same sync execution helper used by `/api/v1/tests/sync`. Once the internal run completes, the adapter produces an OpenAI-like `chat.completion` response and includes AutoAgent-specific debug details in a namespaced extension object.

This keeps executor behavior aligned between the old and new entry points and avoids introducing a separate test pipeline for SDK users.

## API Contract

### Endpoint

- `POST /v1/chat/completions`

### Authentication

- Reuse the existing bearer JWT flow
- The caller first authenticates with `POST /api/v1/auth/login`
- The returned JWT is then passed as `Authorization: Bearer <token>` to `/v1/chat/completions`
- For OpenAI SDK callers, the JWT is used as the SDK `api_key`

### Supported Request Fields

These fields are accepted in the first version:

- `model`
  - Required
  - Interpreted as AutoAgent `target_profile`
- `messages`
  - Required
  - Only the last `role="user"` text message is used
- `metadata`
  - Optional
  - Copied into internal `Sample.metadata`
- `stream`
  - Optional
  - Only omitted or `false` is accepted
- Extension fields at request-body top level:
  - `new_session`
  - `timeout_sec`
  - `retry`
  - `dry_run`

### Unsupported Request Fields

These are explicitly unsupported in the first version and should fail fast with an OpenAI-style error response:

- `stream=true`
- `tools`
- `tool_choice`
- `functions`
- `function_call`
- `n` when not equal to `1`
- `response_format`
- `audio`
- `modalities`
- `parallel_tool_calls`
- Non-text `content`
- Full-history semantics across `system` / `assistant` messages

### Example Client Usage

```python
from openai import OpenAI

client = OpenAI(
    base_url="http://localhost:8000/v1",
    api_key="<jwt-from-/api/v1/auth/login>",
)

response = client.chat.completions.create(
    model="my_profile",
    messages=[{"role": "user", "content": "你好"}],
    extra_body={
        "new_session": True,
        "timeout_sec": 120,
        "retry": 1,
        "dry_run": False,
    },
)

print(response.choices[0].message.content)
```

## Request Mapping

### OpenAI Request To Internal Sample

The compatibility adapter constructs a single internal `Sample`:

- `id`
  - Auto-generated by the compatibility layer
- `prompts`
  - A one-item list containing the last `role="user"` text message
- `target_profile`
  - Taken directly from `model`
- `mode`
  - Derived from the resolved profile platform
- `new_session`
  - Taken from request-body extension field, default `false`
- `timeout_sec`
  - Taken from request-body extension field when provided
- `retry`
  - Taken from request-body extension field, default internal model default
- `dry_run`
  - Taken from request-body extension field, default `false`
- `metadata`
  - Taken from OpenAI `metadata` if present

### Profile Platform To Internal Mode

- `platform: api` -> `mode: api`
- `platform: web` -> `mode: gui_pc_web`
- `platform: android` -> `mode: gui_android`
- `platform: agent_pc` -> `mode: agent_pc`
- `platform: agent_android` -> `mode: agent_android`

This means OpenAI callers do not provide `mode` directly. The profile remains the source of truth for execution type.

## Response Mapping

### Primary Message Content

The compatibility response must expose a single assistant message in `choices[0].message.content`. That final message is chosen using this rule:

```text
If the resolved profile has LLM response extraction enabled:
  use llm_responses[0] when llm_errors[0] is None and llm_responses[0] is non-empty
  otherwise fall back to responses[0]

If the resolved profile does not have LLM response extraction enabled:
  use responses[0]
```

This rule exists because in current practice the LLM-extracted result can be more accurate than the static extractor, but the compatibility layer must not degrade a successful run into an empty response when LLM extraction fails. The adapter therefore prefers LLM output only when it clearly succeeded.

### Mode-Specific Note

For `agent_pc` and `agent_android`, current executors already write the same extracted text into both `responses` and `llm_responses`. The selection rule still holds, but it usually produces the same final content in those modes.

### OpenAI-Shaped Success Response

On success, return a minimal `chat.completion` payload:

```json
{
  "id": "chatcmpl_<sample_id>",
  "object": "chat.completion",
  "created": 1710000000,
  "model": "my_profile",
  "choices": [
    {
      "index": 0,
      "message": {
        "role": "assistant",
        "content": "最终测试结果文本"
      },
      "finish_reason": "stop"
    }
  ],
  "x_autoagent": {
    "sample_id": "s_123",
    "status": "done",
    "attempt_count": 1,
    "duration_ms": 842,
    "responses": ["静态提取结果"],
    "llm_responses": ["LLM提取结果"],
    "llm_errors": [null],
    "logs_dir": "/tmp/...",
    "metadata": {}
  }
}
```

The `x_autoagent` object is intentionally non-standard. It preserves the internal diagnostic shape without polluting standard OpenAI response fields.

## Error Mapping

Errors should be returned in OpenAI-style error format:

```json
{
  "error": {
    "message": "stream=true is not supported",
    "type": "invalid_request_error",
    "param": "stream",
    "code": "unsupported_parameter"
  }
}
```

Recommended mappings:

- Invalid request payload or unsupported fields -> HTTP `400`
- Missing or invalid bearer token -> HTTP `401`
- Unknown target profile -> HTTP `404`
- Internal sample timeout -> HTTP `504`
- Internal execution failure -> HTTP `500`

The adapter should preserve enough detail in `error.message` to make the failure actionable, but should not expose raw stack traces.

## Module Boundaries

Recommended structure:

- `src/autoagent/api/openai_compat.py`
  - FastAPI router for `/v1/chat/completions`
  - Depends on existing bearer auth
- `src/autoagent/openai_compat/schemas.py`
  - Minimal request and response models for the compatibility layer
- `src/autoagent/openai_compat/chat_completions.py`
  - Request validation
  - Profile resolution
  - Request-to-`Sample` mapping
  - `SampleResult`-to-OpenAI response mapping
- Shared sync execution helper
  - Move current `/api/v1/tests/sync` helper into a reusable module that both routers can call

The compatibility router should not import another router module purely to reuse a route-local helper. Shared execution belongs in a small reusable backend helper.

## Validation Rules

The adapter should enforce these constraints:

- `model` must be present and resolve to a valid profile
- `messages` must contain at least one `role="user"` message with text content
- only the last `user` text message is used
- `stream=true` is rejected
- unsupported OpenAI fields are rejected explicitly instead of being silently ignored when they imply behavior the system does not implement
- extension fields must validate against internal types:
  - `new_session`: boolean
  - `timeout_sec`: positive integer
  - `retry`: non-negative integer
  - `dry_run`: boolean

## Testing Strategy

### Integration Tests

Add integration tests for:

- successful `POST /v1/chat/completions` call against an `api` profile
- successful call against a `web` profile
- mapping of `new_session`, `timeout_sec`, `retry`, and `dry_run`
- JWT authentication failure
- unknown `model` / profile
- `stream=true` rejection
- unsupported-field rejection
- fallback from failed `llm_responses` to `responses`
- preference of successful `llm_responses` over `responses`

### Unit Tests

Add unit tests for:

- request validation
- last-user-message extraction
- profile-platform to mode mapping
- final response selection logic between `responses` and `llm_responses`
- OpenAI-style error payload rendering

## Rollout Notes

The first version should be documented as a narrow compatibility layer for sync single-test execution. It is intentionally not a full OpenAI protocol clone. The implementation should prefer explicit errors over silent partial support so SDK callers can quickly understand what the compatibility surface does and does not provide.
