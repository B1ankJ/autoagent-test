# Web Builder Response Selector Fix

Date: 2026-04-27

## Goal

Fix incomplete or polluted web chat responses caused by unstable `response_container_selector` values generated by the Web Builder and by multi-match response extraction during execution.

## Problem

Two related bugs were observed in the web chat flow.

### 1. Builder generated paragraph-level selectors

When the user clicked inside a response paragraph, the Web Builder could emit selectors such as `.qk-md-text`.

That selector was too broad for chat UIs because:

- a single assistant reply may contain multiple paragraph nodes
- a single assistant reply may also use one text wrapper such as `.qk-md-text` around multiple paragraphs
- older replies may reuse the same class
- the selector did not represent the reply container or the latest reply item

This led to YAML profiles that targeted the wrong DOM scope.

### 2. Executor concatenated multiple matched replies

When `response_container_selector` matched more than one node and `new_session=false`, the executor could collect text from multiple assistant replies and return historical content together with the latest answer.

## Root Cause

The Web Builder selector derivation logic optimized for any selector that could point back to the clicked element, but it did not distinguish between:

- unique selectors for generic fields like input and send controls
- latest-message selectors needed for response extraction in chat layouts

It also allowed degenerate fallbacks such as bare tag selectors or repeated paragraph classes.

Separately, the executor used the same selector both to wait for DOM stability and to return response text. For multi-match selectors, that meant the final returned text could span multiple matched nodes.

## Design

### Builder selector generation

For `field=response`, the builder should generate a selector for the latest reply container, not for the clicked text leaf.

The implemented strategy is:

1. Start from the clicked DOM node.
2. Promote from the leaf node to a larger text-bearing ancestor when the leaf is only a paragraph fragment.
3. Walk ancestors to find a repeated message item.
4. Prefer a `:last-child` selector for that repeated item.
5. If the promoted response node needs a nested selector inside that latest item, use a stable relative selector.
6. For non-response fields, continue to generate a unique selector for the clicked element.

The selector generator now also avoids low-value fallbacks:

- no bare `div` selector fallback for meaningful picks
- no acceptance of repeated class selectors as unique selectors
- stable class names such as `qk-markdown` remain usable

### Executor response extraction

Completion detection can still observe the full matched DOM set to determine when output has stabilized.

However, the final returned response should prefer the last non-empty matched node. If that cannot be read, the executor falls back to the stabilized text or the old aggregate collector.

This keeps compatibility with existing profiles while preventing history bleed-through in reused sessions.

## Non-Goals

- no redesign of the Web Builder UX
- no changes to profile schema
- no automatic migration of previously generated YAML files

## Follow-up: Persistent Chrome Profile Recovery

On 2026-04-28 a separate failure mode was observed for web profiles that set `browser.user_data_dir`.

Symptom:

- `launch_persistent_context(...)` failed before navigation
- the Chrome profile directory contained broken `SingletonLock`, `SingletonCookie`, or `SingletonSocket` links from a previous crashed Playwright launch

Adjustment:

- before giving up on persistent-context launch, the executor now checks for broken `Singleton*` symlinks under `user_data_dir`
- if such links are present, it removes only the broken symlinks and retries launch once
- it does not remove live sockets or other profile files

Coverage:

- `tests/unit/test_web_executor_unit.py` verifies stale singleton cleanup and one retry path
